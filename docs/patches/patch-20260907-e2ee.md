# Thread E2EE·개인정보 보호 설계안

작성: 2026-09-07 23:20 (KST)

상태: 제안 — 구현 및 운영 전환 미승인

관련 작업: [#41](../tasks/0041.md)

대상: Desktop 편집·오프라인 동기화, Mobile 조회·기기 승인, API, RMS 배포 신뢰

## 1. 목적과 제안 결론

사용자가 자신의 할 일·메모·일정을 서비스 운영자에게 맡기지 않고도 여러 기기에서 사용할 수 있게 한다. 내용은 승인된 기기에서만 복호화하고 서버는 암호문과 동기화에 필요한 최소 정보만 보관한다.

권장안은 계정마다 하나의 암호화 보관함(vault), 기기별 키, 복구 키를 사용하는 E2EE다. Google/Thread 로그인은 계정 접근을 인증하고, 보관함 잠금 해제는 별도로 처리한다. 로그인 비밀번호를 데이터 키로 직접 사용하지 않는다. 기본 복구 방법은 기존 기기 승인 또는 무작위 복구 키다.

신규 보관함은 처음부터 암호화한다. 기존 사용자는 준비된 새 클라이언트에서 설명과 복구 수단 확인 후 계정 단위로 전환한다. 전환한 계정의 평문 동기화는 서버에서 영구 차단한다. 기존 v2 전환의 일괄 정책을 E2EE에 자동 적용하지 않는다. 키 보존과 복구 확인이 필요한 별개의 변경이므로 이 정책은 구현 전 제품 결정 대상이다.

이 문서는 구현 요구사항과 설계 선택지를 구체화한 것이다. 현재 제품이 E2EE라는 뜻이 아니며, 아래 알고리즘·프로토콜 조합은 외부 암호 설계 검토와 플랫폼 검증을 거쳐 확정해야 한다.

## 3. 보호 약속과 위협 모델

### 3.1 보호하는 대상

- DB 덤프, 서버 백업, 서버 디스크 또는 API 프로세스를 확보해도 보호된 본문을 해독할 수 없도록 한다.
- API 운영자가 관리자 계정을 사용해도 보관함 키를 얻을 수 없도록 한다.
- API/프록시/CDN이 보는 요청 본문에도 할 일 평문이 없도록 한다.
- 서버가 기기 공개키를 바꿔치기해 새 기기를 끼워 넣는 시도를 기존 기기의 승인·서명 검증으로 막는다.
- 변조·잘못된 계정/항목으로 암호문 이동·권한 없는 쓰기는 클라이언트에서도 검증한다.

### 3.2 보장하지 않는 것

| 상황 | 한계와 대응 |
| --- | --- |
| 잠금 해제된 PC의 악성코드·관리자 권한·키로거 | 화면과 메모리 내용 탈취 가능. E2EE만으로 해결 불가 |
| 정당한 서명 권한까지 탈취한 악성 앱 업데이트 | 앱이 복호화한 내용을 유출할 수 있음. 배포 권한 분리·감사로 위험 축소 |
| 서버가 암호문을 삭제하거나 요청을 차단 | 가용성 보장 불가. 기기 로컬 사본·사용자 암호화 백업으로 복구 |
| 서버가 기기별로 서로 다른 이력을 보여줌 | 서명만으로 완전 탐지 불가. 저장된 checkpoint·기기 간 대조로 일부 탐지 |
| 모든 기기와 복구 키 분실 | 운영자도 내용 복구 불가. 보관함 재설정은 별도 파괴적 절차 |
| 이관 전 평문을 운영자가 이미 복사 | 사후 암호화로 과거 열람·복사를 취소할 수 없음 |
| 사용자가 텍스트로 내보내거나 공유·스크린샷 | 공유 이후에는 해당 파일과 수신자의 보호 정책에 따름 |

“운영자도 현재 암호화된 본문을 해독할 키가 없다”는 약속과 “어떤 공격에도 절대 읽을 수 없다”는 약속을 구분한다. 후자는 사용하지 않는다.

## 4. 암호화 범위와 남는 메타데이터

| 데이터 | 제안 저장 방식 | 이유 |
| --- | --- | --- |
| 할 일 제목·메모·하위 항목 제목 | 암호화 | 핵심 개인정보 |
| 마감일·완료 여부·완료일·반복 규칙·업무 생성일 | 암호화 | 생활 패턴과 일정도 보호 |
| 카테고리 이름·색·secret/locked | 암호화 | 숨긴 항목 여부 자체도 개인정보 |
| 분류 연결·하위 항목 관계·사용자 정렬 순서 | 암호화된 필드/관계 객체 | 서버 조인 대신 클라이언트에서 계산 |
| 디바이스 별칭·로컬 검색 인덱스 | 암호화, 검색은 기기 내 | 기기 이름에 실명 포함 가능 |
| 계정 UID, 로그인 이메일/Google 연결 정보 | 서버 인증 DB에 보존 | 로그인·계정 운영에 필요, 별도 접근 제한 |
| vaultId, 무작위 objectId, deviceId, 공개키 | 서버에 공개 | 전달·승인·중복 방지 |
| 암호문 길이, 접근 시각, IP, sequence, tombstone, 암호화 필드 슬롯 | 서버에서 관찰 가능 | 동기화·용량 제한에 필요 |

본문은 공개하지 않지만 항목 수·변경 빈도·트래픽 양·필드 슬롯으로 활동을 추측할 수 있다. 이 설계는 익명 통신이나 완전한 메타데이터 은닉을 제공하지 않는다.

v1 암호화 포맷은 엔티티 종류를 암호화된 내부 헤더에 둔다. 서버는 일반 object와 고정된 숫자 field slot만 취급한다. slot만으로 일부 동작을 추측할 수 있다는 점은 남는다. 필드별 길이를 일정 구간으로 패딩하는 방안은 벤치마크 후 결정하고, 최소 출시에는 길이 은닉을 약속하지 않는다.

HTTPS는 계속 필수다. Cloudflare Tunnel/외부 TLS 구성과 독립적으로 요청 본문을 클라이언트에서 먼저 암호화한다.

## 5. 키 구조

### 5.1 키 종류

| 키 | 생성·보관 | 역할 |
| --- | --- | --- |
| Vault data key VDK[g] | 최초 기기에서 CSPRNG 32바이트 생성 | 세대 g의 데이터 암호화 기준 |
| Device encryption key pair | 기기에서 생성, 비밀키는 OS 키 저장소로 보호 | 해당 기기용 VDK envelope 수신 |
| Device signing key pair | 기기에서 별도 생성 | 수정·기기 승인·키 변경 서명 |
| Recovery secret R | 무작위 32바이트, 사용자에게 복구 코드/파일 제공 | VDK keyring 및 복구 권한 비밀키를 감싼 bundle 해제 |
| Recovery authority signing key | 최초 기기 생성, 비밀키는 복구 bundle 내부만 | 기존 기기가 전혀 없을 때 새 기기 승인·키 교체 |
| Local DB key LDK | 기기·보관함마다 별도 생성 | 로컬 SQLite·검색·outbox·복구 임시본 보호 |

VDK, R, 기기 비밀키는 서버에 평문으로 전송하지 않는다. 서버에는 공개키, 서명된 승인 기록, 암호화된 key envelope만 둔다. 환경 변수·빌드 설정·JWT 비밀값에 사용자 데이터 키를 넣지 않는다.

데이터 키와 기기 서명 키를 분리하므로 모바일이 데이터를 읽을 수 있어도 정상 클라이언트에서는 할 일 변경 권한을 가지지 않는다. 기기 해지 후 이미 복사한 내용이나 키를 원격 삭제할 수는 없다.

### 5.2 암호 기본형 제안

- 내용과 대칭키 envelope: 검증된 libsodium 구현의 XChaCha20-Poly1305 AEAD.
- 매 암호화마다 CSPRNG로 새 24바이트 nonce. 재전송은 이미 만든 동일 envelope를 보내며 같은 nonce로 다른 내용을 다시 암호화하지 않는다.
- 항목·필드·용도별 키는 VDK[g]에서 HKDF-SHA-256으로 도메인을 분리해 파생한다. 입력은 길이와 타입이 명확한 결정적 인코딩으로 정의한다.
- 기기용 키 전달: X25519 기반 libsodium sealed box로 암호화하고 승인 기기의 Ed25519 서명을 별도로 검증한다. sealed box만으로 보낸 사람 신원을 증명하지 않는다.
- 모든 수정과 승인 이벤트는 Ed25519 서명. 직렬화 포맷은 deterministic CBOR를 후보로 하고 각 언어별 golden vector를 고정한다.
- recovery R도 용도별 KDF를 사용한다. 사람의 비밀번호와 다른 고엔트로피 비밀이므로 기본 복구 코드에 password KDF를 적용할 필요는 없다.

알고리즘 조합은 Thread 자체 암호 라이브러리로 재구현하지 않는다. Desktop/Mobile에서 동일 라이브러리·포맷을 사용할 수 있는지, native binary 공급 경로와 메모리 사용까지 구현 착수 시 검증한다. [libsodium 메시지 암호화 지침](https://libsodium.gitbook.io/doc/secret-key_cryptography/encrypted-messages), [sealed boxes](https://libsodium.gitbook.io/doc/public-key_cryptography/sealed_boxes)를 참고한다.

### 5.3 Envelope와 서명 범위

개념 형식이며 복사해서 구현할 최종 wire schema는 아니다.

```text
signedMutation = {
  protocolVersion, cryptoSuite, vaultId, vaultEpoch, membershipRevision,
  deviceId, deviceCounter, mutationId, expectedObjectVersion,
  changes: [
    { objectId, fieldSlot, keyGeneration, nonce, ciphertext }
  ],
  deviceSignature
}
```

AEAD의 AAD는 protocolVersion, suite, vaultId, vaultEpoch, objectId, fieldSlot, keyGeneration, mutationId, deviceId를 포함한다. 다른 사용자·항목·필드로 암호문을 옮기면 인증에 실패해야 한다.

서명은 expected version, 변경 전체, nonce, ciphertext, 기기 counter, 멤버십 revision까지 포함한다. 서버가 나중에 부여하는 seq/수신시각은 발신자 서명에 포함할 수 없다. 서버 seq를 발신자가 보증한 원본 순서로 오해하지 않는다. pull/snapshot은 검증에 필요한 원본 서명 envelope와 해당 시점의 승인 기록을 보존한다.

## 6. 가입·로그인·새 기기 연결

### 6.1 최초 보관함 생성

1. Google/Thread 로그인으로 계정 인증.
2. 기기에서 VDK, 기기 키, 복구 authority와 R 생성.
3. 계정에 하나의 genesis 생성 요청. 서버 uniqueness 조건으로 동시 생성 충돌 차단.
4. genesis에는 vaultId와 recovery 공개키, 최초 기기 공개키·역할을 묶고 서명한다.
5. 첫 기기는 genesis fingerprint를 로컬 pin한다. 복구 키트에도 fingerprint와 vaultId를 포함한다.
6. 복구 코드 저장 및 재입력 검증. 확인 전에는 “복구 준비 필요”로 표시.
7. 로컬 키 보호와 복구 확인이 성공하면 암호화 동기화를 시작한다.

서버가 반환한 새로운 genesis로 기존 보관함을 조용히 교체하지 않는다. 계정에 보관함이 있는데 키가 없는 경우 빈 보관함 생성 대신 기기 승인/복구 화면을 띄운다.

### 6.2 기존 기기에서 새 Desktop/Mobile 승인

로그인만으로 키를 지급하지 않는다. 새 기기는 자기 공개키·요청 nonce·vaultId·유효시간을 담은 연결 요청을 만들고 QR 또는 비교 코드로 표시한다.

기존 기기는 사용자 존재 확인 후 QR의 공개키 fingerprint를 대조하고 권한을 선택한다. Desktop 기본은 read/write, Mobile 기본은 read다. 짧은 코드만으로 서버가 고른 키를 믿지 않으며, QR 전문 또는 충분한 엔트로피의 transcript 비교와 시도 제한이 필요하다.

승인 기기는 membershipRevision에 대해 compare-and-swap으로 승인 기록을 서명하고 새 기기 공개키에 VDK keyring을 암호화한다. 새 기기는 pairing에서 확보한 genesis fingerprint, 승인 체인, 자신의 키 해시와 nonce를 검증한 뒤 저장한다. 요청은 10분 만료·일회성 소비를 기본 제안으로 둔다.

기기 역할과 canAuthorizeDevices를 분리한다. 조회용 모바일은 기본적으로 새 기기를 승인하지 못한다. 기기 승인은 보관함 내용을 수정하는 권한과 별개의 권한이다.

### 6.3 모든 기기 분실 시 복구

계정 재로그인 → 복구 키트 입력 → 로컬 bundle 복호화 → vault fingerprint 확인 → recovery authority로 새 기기 승인 → 필요하면 기존 기기 전체 해지·키 세대 교체 순서다.

복구 키는 웹페이지, 서버 API, 문의 폼에 입력하지 않는다. 앱의 로컬 입력 화면에서만 사용한다. Google OAuth token이나 로그인 비밀번호만으로 VDK를 재생성하지 않는다.

복구 코드에 checksum을 붙여 오타를 검출하되 checksum은 보안 강도를 높이는 요소가 아니다. 복구 파일에는 vaultId, genesis fingerprint, 암호화된 keyring bundle, 포맷 버전을 담는다. R과 bundle을 한곳에 함께 저장하면 키트 소지자가 내용을 읽을 수 있음을 표시한다.

### 6.4 비밀번호 변경·복구 코드 교체

계정 비밀번호 재설정은 인증 수단만 바꾼다. 데이터를 풀어주는 관리자 reset endpoint는 만들지 않는다.

복구 코드 분실 상태에서도 승인 기기가 남아 있으면 새 R과 recovery authority를 생성하고 멤버십에 교체를 기록할 수 있다. 코드 유출 의심 시 envelope만 다시 감싸는 것으로 끝내지 않고 VDK도 교체한다. 옛 코드와 옛 bundle을 이미 복사한 공격자의 과거 데이터 접근을 취소할 수는 없다.

암호 기반 보관함 비밀번호는 초기 출시에서 제외하는 것을 권장한다. 추가한다면 로그인 비밀번호와 분리하고 Argon2id를 사용한다. RFC 9106의 64MiB, t=3, p=4 프로파일을 평가 출발점으로 삼되 실기기 측정과 offline guessing 위협 검토 후 정한다. 이 수치는 Thread에서 검증된 설정이 아니다. [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)

## 7. 클라이언트 저장과 잠금

OS 키 저장소는 LDK·기기 비밀키·VDK envelope를 보호한다. Electron safeStorage를 쓴다고 기존 SQLite 파일이 자동 암호화되는 것은 아니다.

권장 로컬 저장은 SQLCipher 등 검증된 SQLite 전체 암호화 계층이며 confirmed/visible/outbox/recovery/search를 모두 포함한다. WAL, journal, 임시파일, crash dump, 자동 DB 백업도 범위에 넣는다. 현재 sqlite3 드라이버를 유지하면서 payload만 암호화하면 검색·인덱스·임시파일에 평문이 남을 수 있으므로 같은 수준으로 홍보하지 않는다.

Windows DPAPI는 동일 로그인 사용자 권한의 다른 프로세스로부터 완전한 격리를 보장하지 않는다. macOS Keychain은 앱 서명 연속성을 검증해야 한다. Linux에서 safeStorage backend가 basic_text라면 키 영속화를 거부하고 보안 저장소 설정 안내를 제공한다. [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

현재 Electron 23 API 가용성과 최신 문서 차이를 검증하고 지원되는 Electron으로의 업그레이드를 선행 과제로 둔다.

잠금 UX 제안:

- 화면 잠금·절전 시 즉시 보관함 잠금, 기본 유휴 5분 후 잠금.
- 잠금 후 렌더러 목록·검색·메모를 비우고 복호화 IPC와 DB 연결을 닫는다.
- OS 인증 또는 별도 설계된 로컬 재인증 성공 후 키 사용을 재개한다. 단순 “열기” 버튼은 보안 잠금으로 부르지 않는다.
- 메모리 키는 가능한 한 제거하되 JS GC·OS swap 특성상 완전 zeroization을 약속하지 않는다.
- 잠금 상태에서는 불투명 ciphertext 수신·보관만 가능하다. 새 사용자 수정 서명과 본문 기반 알림은 중단한다.
- 잠금 화면 알림 기본값은 “예정된 할 일이 있어요”. 제목 공개는 사용자 선택.
- dev와 prod 사이 자동 키 복사 금지. 계정 전환 때 이전 렌더러 state·키·DB 핸들 정리.

렌더러는 표시할 평문만 받으며 키는 main/별도 제한된 프로세스에서 관리한다. nodeIntegration=false, contextIsolation=true, sandbox 적용 가능성 검증, 좁은 preload API와 sender 검증, CSP, 외부 탐색 차단을 출시 게이트에 넣는다. “키를 main에 뒀다”만으로 침해된 렌더러의 평문 유출을 막았다고 설명하지 않는다.

## 8. 암호문 동기화 설계

### 8.1 유지하는 원칙

오프라인 우선, durable outbox, mutationId 멱등성, 단조 증가 서버 cursor, pull/snapshot, 재접속 복구를 유지한다. 서버의 역할은 계정 권한·기기 서명·용량·키 세대·멤버십 검증과 암호문 저장이다.

정렬·기한 필터·검색·카테고리 조인·반복 규칙 검증은 복호화한 클라이언트가 맡는다. 서버에는 제목 검색 API나 관리자 복호화 기능을 만들지 않는다. 조회용 Mobile도 키 승인·복호화·snapshot/delta·tombstone·포맷 버전은 지원해야 한다.

### 8.2 필드 단위 암호화와 충돌

할 일 전체 JSON 하나를 암호화하면 제목과 메모를 서로 다른 기기에서 고쳐도 충돌한다. 따라서 독립 필드는 별도 AEAD envelope로 저장하고, 필드 간 불변식이 필요한 변경은 원자적 group으로 묶는다.

기본 정책은 “서버가 암호문을 임의로 합치지 않는 optimistic concurrency”다. 서버는 expectedObjectVersion이 현재와 다르면 충돌과 최신 암호문을 반환한다. 클라이언트는 base·remote·local을 복호화하여 다른 필드 변경이면 자동 재적용하고 새 mutationId로 서명한다. 같은 필드 변경이면 양쪽 사본을 로컬 복구함에 보존하고 선택을 요청한다. 제목 한쪽을 자동 폐기하지 않는다.

재시도는 기존 envelope 그대로, rebasing한 새 변경은 새 mutationId·nonce를 사용한다. 네트워크 ACK 유실과 의미가 달라진 편집 재시도를 구분한다. 시간 동기화가 안 된 기기의 시계를 충돌 승패 기준으로 사용하지 않는다.

삭제는 generic tombstone으로 처리한다. 삭제와 오프라인 편집이 충돌하면 자동 부활시키지 않고 “삭제된 항목의 복구 가능한 편집”으로 보관한다. 관계 dangling reference는 클라이언트에서 탐지·복구하며 서버 SQL FK로 암호화된 관계 의미를 검증할 수 없다.

### 8.3 반복 일정과 순서

기존 서버 recurrence 엔진 대신 Desktop의 버전 고정된 로컬 엔진을 사용한다. 시간대, DST, 월말 처리, 반복 기준 시각을 암호화된 규칙에 명시하고 기존 v2 동작과 차이는 golden fixture로 검증한다.

반복 완료는 원본 업데이트와 다음 발생 객체 생성의 원자적 batch다. vault별 비밀 파생키로 seriesId+generation의 결정적 occurrenceId를 만들고 서버는 일반 objectId uniqueness와 batch CAS로 중복 생성만 막는다. 경쟁 batch가 패배하면 승자의 결과를 복호화·검증한 뒤 병합한다. 서버는 반복 규칙 자체를 읽거나 실행하지 않는다.

정렬 rank 역시 암호화된다. 서버는 의미를 모르며 클라이언트들이 동일 정렬 규칙·동률 시 objectId 순서를 적용한다. 완료·다음 발생·관계 변경처럼 묶여야 하는 group은 부분 수락하지 않는다.

### 8.4 서버 schema / endpoint 제안

새 테이블로 추가하고 기존 migration 파일을 수정하지 않는다.

| 테이블 | 핵심 정보 |
| --- | --- |
| vaults | vault_id, account_id, mode, epoch, suite, membership_revision, current_key_generation |
| vault_devices | 공개키, role, 승인·해지 기록 참조 |
| vault_membership_events | 서명된 genesis/approve/revoke/recover 이벤트와 이전 digest |
| vault_key_envelopes | 수신 기기·키 세대·암호문·승인 서명 |
| encrypted_objects / encrypted_fields | 무작위 ID, 불투명 slot, 암호문, nonce, 세대, tombstone, revision |
| encrypted_changes / receipts | 원본 signed mutation, 서버 seq, 멱등 결과 |
| encrypted_snapshots | 검증 가능한 원본 필드 envelope·서명 provenance 및 manifest |
| vault_migrations | migrationId, freezeSeq, manifestDigest, 상태·수량·purge 작업 ID |

개념 API: /v3/vault, /v3/devices/pairing, /v3/devices/approve, /v3/devices/revoke, /v3/sync/push, /v3/sync/pull, /v3/sync/snapshot, /v3/migration/prepare|commit|status.

UID는 인증 principal에서 결정한다. 요청 body의 accountId를 신뢰하지 않는다. 복구·승인 변경에는 JWT만이 아니라 유효한 보관함 승인 서명이 필요하다. 서버 관리자 JWT로 이를 우회하는 경로는 없다.

실제 endpoint별 request/response JSON schema, 최대 크기, CAS 범위, 오류 코드와 서명 canonical encoding은 구현 전 프로토콜 명세 단계에서 고정한다.

### 8.5 스냅샷·롤백·악성 서버

스냅샷에는 각 필드의 원본 서명 provenance가 남아야 한다. 복호화된 값을 다시 저장한 서버 JSON을 신뢰하지 않는다. 클라이언트는 마지막 신뢰한 membership revision, key generation, epoch, cursor와 checkpoint digest를 로컬에 보존한다.

이전 key generation의 새 쓰기, 보았던 멤버십보다 과거 상태, 동일 mutationId에 다른 내용이 오면 동기화를 중단한다. 새 기기는 승인 기기/복구 키트가 가진 checkpoint도 전달받는다.

이것만으로 서버가 일부 기록을 숨기는 것, 기기별 분기 이력, 모든 기기를 잃은 뒤의 과거 상태 제공을 완전히 탐지할 수는 없다. 독립 key transparency/log witness와 기기 간 checkpoint 교환은 후속 검토 영역이다. 첫 출시에서 “악성 서버의 모든 롤백까지 탐지”를 약속하지 않는다.

## 9. 기기 해지와 키 회전

기기 해지 시 refresh token·sync 권한을 폐기하고 membership revision을 높인다. 남은 승인 기기가 새로운 VDK[g+1]을 생성해 활성 기기와 새 복구 bundle에만 전달한다.

새 쓰기는 새 세대만 허용하고 옛 키로 쓰려는 offline 기기는 pull·멤버십 검증 후 재암호화한다. 해지된 기기의 미전송 변경은 사용자 요청 시 신뢰된 기기에서 별도 가져오기·검토해야 하며 자동 재승인하지 않는다.

현재 객체는 배경에서 새 세대로 재암호화하고 CAS로 중간 수정 유실을 막는다. 옛 log/snapshot은 retention과 키 보유 정책에 맞춰 정리한다. 전환 동안 구키가 필요한 envelope가 있으면 구키를 먼저 버리지 않는다.

기기를 잃어도 과거 사본은 회수되지 않는다. “이 기기의 앞으로의 동기화와 새 키 접근을 차단했습니다”라고 안내한다. 공유 vault key 모델은 메시지마다 forward secrecy를 제공하지 않는다.

## 10. 기존 평문 데이터 마이그레이션

### 10.1 목표

실제 내용 암호화는 사용자 기기에서 수행한다. 서버에서 암호화한 뒤 키까지 같이 저장하는 전환은 하지 않는다. 사용자 할 일·관계·pending·recovery item의 누락 0개, 중단 후 재개, 중복 업로드 안전성을 필수 조건으로 둔다.

서버 schema 자동 migration은 새 테이블 생성까지만 한다. 계정 데이터 변환은 사용자가 승인한 클라이언트 coordinator의 별도 작업이다. 오프라인 사용자는 다음 로그인 전까지 전환되지 않을 수 있으며 그 계정의 기존 서버 데이터는 계속 평문이라는 점을 운영 지표에서 구분한다.

### 10.2 상태 전이

```text
LEGACY → PREPARING → FROZEN → UPLOADING → VERIFIED → E2EE_ACTIVE → PURGE_PENDING → COMPLETE
                    ↘ commit 전 취소: LEGACY + 원본 유지
```

1. PREPARING: 앱 지원 버전·디스크 여유·키 저장소·복구 코드 확인. 기존 로컬 DB를 보존하고 별도 암호화 DB에 작업한다.
2. coordinator 기기 지정. 연결 가능한 기기는 outbox 전송을 완료한다. 오프라인 기기가 전부 돌아올 때까지 무기한 기다리지는 않으며 후속 구기기 복구 흐름을 제공한다.
3. FROZEN: 서버가 해당 계정 v2 쓰기를 원자적으로 차단하고 freezeSeq 고정. 모든 v2 push 경로·동시 요청에 gate 적용. 이후 편집은 coordinator의 암호화 로컬 pending에만 보존한다.
4. freezeSeq 기준 스냅샷을 페이지별로 내려받아 기존 local confirmed/pending과 대조한다. 처음부터 전체 데이터를 RAM에 올리지 않는다.
5. 최초 기기에서 암호화하고 staging vault에 재시도 가능한 청크로 업로드한다. 작업 상태는 암호화된 로컬 DB에 저장한다.
6. 다시 내려받아 복호화하고 원본 필드·항목·관계·반복 설정·tombstone·pending을 대조한다. plaintext hash는 서버로 올리지 않는다. 서버에는 ciphertext manifest hash만 전송한다.
7. VERIFIED: 로컬 검증 결과 및 전체 manifest에 기기 서명. 원본 snapshot의 범위와 page count가 일치해야 한다.
8. commit: 서버 transaction에서 migrationId, freezeSeq, manifest, epoch를 CAS 검증하고 E2EE_ACTIVE로 전환. 신규 v3 pull만 허용. 재시도는 기존 결과를 반환한다.
9. 클라이언트가 commit 상태를 재조회해 확인한 뒤 새 DB를 주 DB로 전환한다. ACK 유실을 실패로 오인해 원본을 삭제하지 않는다.
10. pending을 v3 outbox로 변환·전송한다. 사용자 확인과 운영 purge 정책을 충족한 후 평문 사본을 정리한다.

PREPARING/FROZEN 단계의 coordinator 종료·디스크 부족·세션 만료는 체크포인트에서 재개한다. commit 전 취소는 staging만 폐기하고 원본 v2를 재개할 수 있다. commit 후에는 평문 모드로 롤백하지 않고 암호문 모드에서 복구한다. 오래된 lease 만료만으로 자동 전환/삭제하지 않는다.

전환용 서명과 수량 검증은 정직한 서버에서의 무결성을 확인할 뿐, 서버가 평문을 모두 지웠음을 암호학적으로 증명하지 못한다.

### 10.3 늦게 돌아온 구기기

구버전에는 UPDATE_REQUIRED를 반환하고 v2 push를 수락하지 않는다. 업데이트는 데이터 폴더를 지우지 않는다.

새 앱은 현재 vault mode를 확인하고 먼저 기기 승인/키 복구를 진행한다. 기존 SQLite와 outbox를 읽기 전용으로 열어 미전송 변경만 변환한다. 이미 있는 항목에 무조건 덮어쓰지 않고 동일 필드 충돌과 삭제를 사용자 복구함에서 해결한다. 변환 오류를 이유로 local reset이나 silent discard를 하지 않는다.

기존 평문 로컬 DB도 검증 후 정리 대상이다. 키를 잃거나 승인에 실패하면 원본을 보존하고 자동 삭제를 멈춘다.

### 10.4 과거 백업·로그 정리

검토할 범위는 tasks/categories/subtasks, v1 blocks/transactions, v2 change logs/snapshots/receipts, read replica, binlog, dump, EBS snapshot, 임시 SQL 파일, CI fixture, 지원 첨부파일, 로그다. 실제로 존재하는지는 운영자가 inventory로 확인한다.

제안 보존 정책은 전환 검증 후 운영 평문 정리 7일 이내, 기존 일반 백업 최대 30일 이내 만료다. 현재 운영 보존 설정을 확인한 값이 아니며, 법적·운영 제약과 복구 요구를 검토한 후 확정해야 한다.

SQL DELETE만으로 InnoDB 페이지·WAL·SSD·기존 스냅샷의 물리적 삭제를 보장하지 않는다. 암호화 스토리지 키 폐기 역시 해당 키로 보호된 모든 사본과 서비스 영향이 확인될 때만 계획한다.

복원 runbook에 삭제 대상 계정의 purge ledger 재적용을 포함한다. 옛 DB를 복원해 평문 계정을 다시 서비스하는 사고를 방지한다. 공유 백업이라 사용자 한 명만 즉시 지울 수 없다면 만료 예정일을 정직하게 표시한다.

“신규 데이터 암호화 완료”와 “기존 서버 평문 사본 정리 완료”를 UI와 운영 지표에서 따로 기록한다. 운영자의 삭제 확인은 독립 검증된 사실이 아니라는 한계도 공개한다.

## 11. 사용자가 이해할 수 있는 보안 UX

### 11.1 보관함 상태 화면

메인 화면에는 작은 잠금 상태만 표시하고, 자세한 내용은 설정 → 개인정보 보호에서 제공한다.

| 상태 | 표시 문구 예시 | 사용자 행동 |
| --- | --- | --- |
| 기존 계정 전환 전 | 현재 데이터는 서버에서 처리됩니다 | 보호 전환 설명 열기 |
| 전환 중 | 내 기기에서 데이터를 암호화하고 있어요 | 진행 수량·재개·실패 이유 |
| 새 데이터 보호 활성 | 할 일과 메모는 승인된 기기에서만 열 수 있어요 | 승인 기기·마지막 동기화 보기 |
| 과거 백업 정리 대기 | 기존 서버 백업 정리가 남아 있어요 | 대상·예정일·보존 이유 |
| 복구 미준비 | 기기를 모두 잃으면 복구할 수 없어요 | 복구 키 저장·확인 |
| 변조/알 수 없는 키 | 데이터 확인에 실패해 동기화를 멈췄어요 | 원본 보존·안전한 재연결 |

“군사급”, “100% 안전”, “운영자가 절대 못 본다”, “검증 완료” 같은 근거 없는 문구를 사용하지 않는다. “보호 활성”은 실제 키 생성·검증·전환 commit이 끝난 로컬 상태와 일치해야 하며 서버 설정 하나로 켜지지 않는다.

### 11.2 복구 안내와 일상 동작

가입 화면에서 다음 내용을 짧게 설명하고 상세 설명은 펼침으로 제공한다.

> 할 일은 내 기기에서 암호화됩니다. 새 기기를 연결하려면 기존 기기의 승인 또는 복구 키가 필요합니다. 둘 다 잃으면 Thread도 내용을 복구할 수 없습니다.

복구 키 저장 후 일부 구간 재입력과 복구 bundle 실제 해제 확인으로 검증한다. 사용자가 “나중에”를 선택할 수 있다면 그 기간에는 로컬 편집만 허용하고 완료 배지를 표시하지 않는 안을 권장한다.

기기 목록에는 별칭·종류·최종 접속·승인 시각·read/write 역할·기기 해지를 제공한다. 운영자는 지원 과정에서 복구 키·비밀번호·할 일 원문을 요구하지 않는다.

기존 카테고리 자물쇠는 “화면에서 숨기기”와 “보관함 암호화”를 분리해 설명한다. 개별 카테고리 잠금이 별도 암호 키로 보호되지 않는 한 추가 암호화라고 표현하지 않는다.

내보내기는 기본적으로 암호화된 Thread 백업을 제안한다. 일반 텍스트/CSV를 선택하면 그 파일은 암호화되지 않는다는 안내와 저장 위치 확인을 제공한다. 클립보드 자동 삭제는 값이 바뀌지 않았을 때만 수행하고 OS 클립보드 기록·타 앱 사본까지 삭제한다고 약속하지 않는다.

## 12. API 운영·로그·업데이트 신뢰

관리자는 서비스 상태·암호문 저장량·오류 분류·릴리스 상태만 조회한다. 보관함 원문 조회, 키 다운로드, 관리자 복호화 버튼은 없다.

로그에는 request ID, 오류 코드, 크기·지연·집계량만 허용한다. JWT, pairing QR, recovery code, key envelope 원문, 평문 diff, 전체 요청 body와 crypto exception buffer는 제외한다. 사용자 이메일·IP 등 메타데이터 보존도 최소 기간을 별도 정의한다.

RMS alert 또는 mandatory 플래그는 보관함 키와 관련이 없다. API/RMS 침해가 악성 설치 파일 배포로 이어지면 E2EE 보호가 무너질 수 있으므로 다음을 출시 선행 조건으로 둔다.

- 신뢰된 공개키로 manifest 서명, 파일 digest·길이·버전·플랫폼 검증 후에만 설치 파일을 허용한다.
- 다운로드 파일 자체의 digest를 검증하고, 같은 RMS가 보내는 서명 없는 checksum만 믿지 않는다.
- 운영자 웹 인증과 release signing 권한 분리. 키를 RMS 컨테이너·일반 env에 두지 않는다.
- 만료·rollback 방지·서명키 교체·오프라인 root·다중 승인 정책을 검증된 업데이트 프레임워크로 평가한다.
- Windows/macOS 플랫폼 서명과 배포 manifest 검증을 함께 사용한다.
- mandatory는 서명된 정책에도 묶는다. 서버의 플래그 하나가 서명 검증·기기 승인·복구 동의를 우회하지 않는다.
- 실제 패키지 설치/시작/업데이트 검증을 릴리스 게이트로 둔다. 1.1.1/1.1.2의 build metadata 누락 사례를 재현 테스트로 유지한다.

오픈소스, 재현 가능한 빌드, 변경 이력, 독립 보안 리뷰 공개를 신뢰 수단으로 삼는다. 코드 공개 자체를 보안 감사 완료로 표시하지 않는다.

## 13. 용량·속도·운영 비용

서버 내용 검색과 반복 계산은 줄지만 서명 검증, envelope, 원본 provenance 보관 비용이 늘어난다. 항목 전체 재암호화보다 필드 단위 전송이 작지만 작은 값에도 nonce·tag·서명 오버헤드가 있다.

새 기기는 전체 암호문 다운로드·로컬 인덱스 생성이 필요하다. 대량 메모와 느린 모바일에서는 최초 연결이 오래 걸릴 수 있어 페이지별 진행률과 중단/재개가 필수다. 잠긴 모바일의 백그라운드 조회는 제한될 수 있다.

측정 fixture는 1천/1만/10만 항목, 긴 메모, 1천 pending, 반복·삭제·관계 혼합으로 한다. 현재 성능의 p50/p95, 메모리 최대치, 첫 동기화 시간, 암호문 크기, 배터리 비용과 비교한다. 수치는 측정 전 약속하지 않고 최소 사양 기기에서 출시 기준을 정한다.

## 14. 검증·출시 게이트

| 영역 | 반드시 확인할 시나리오 |
| --- | --- |
| 암호 포맷 | Desktop/Mobile golden vectors, nonce 중복 방지, AAD·서명 한 바이트 변조, 다른 vault/slot 재사용 거절 |
| 키·승인 | 서버 공개키 바꿔치기, QR replay·만료, 동시 승인 CAS, 복구 authority 교체, readonly 서명 쓰기 거절 |
| 분실·회전 | 기기 전체 분실 후 복구, 해지 기기의 다음 세대 접근 차단, offline outbox 재암호화 |
| 동기화 | ACK 유실·중복·순서 변경·동시 편집·삭제 충돌·부분 batch rollback·snapshot 검증 |
| 반복 일정 | 월말·윤년·DST·시간대 변경·다중 기기 동시 완료·결정적 발생 ID |
| 로컬 보호 | SQLite/WAL/검색/임시파일에 synthetic 민감 문구 미노출, 잠금 후 IPC 거절, 계정/dev/prod 분리 |
| 마이그레이션 | 각 단계 강제 종료·디스크 부족·만료 토큰·freeze 경합·commit 응답 유실·구기기 pending 복구 |
| 운영 누출 | synthetic 문구가 DB·요청 캡처·로그·새 백업에 없음; UID/IP 등 의도된 메타데이터는 별도 목록 확인 |
| 배포 | 잘못된 서명·만료 manifest·rollback 거절, 실제 설치본 기동·덮어 설치·키 접근 유지 |
| UX | 복구 코드 저장/분실을 비개발자가 설명 가능, 전환 상태와 백업 잔존 상태 구별 |

민감 문구 검색 통과만으로 암호 설계가 안전하다는 증명이 되지는 않는다. 암호 프로토콜 리뷰, 권한 경계 테스트, 독립 침투 테스트를 별도 수행한다. 실제 개인 DB를 자동 열람하는 검증은 하지 않으며 synthetic fixture로 시작한다.

정식 E2EE 안내를 내기 위한 게이트는 프로토콜 동결·외부 설계 리뷰, 키 복구 실기기 검증, 운영 purge/restore 리허설, 서명된 업데이트 경로, Desktop/Mobile 상호 운용 검증이다. Mobile UI 개편은 범위 밖이어도 읽기 프로토콜과 키 승인은 이 게이트에 포함한다.

## 15. 제안 실행 순서와 미확정 결정

1. 위협 모델·제품 약속·기존 사용자 전환/백업 정책 승인.
2. Electron 경계·지원 버전·서명된 업데이트·키 저장소 실험.
3. crypto/wire schema와 테스트 벡터, 멤버십·복구·회전 모델 외부 검토.
4. 격리된 synthetic vault로 API·Desktop·Mobile 조회 왕복.
5. 암호화 로컬 DB·offline 편집·충돌·반복·잠금 UX.
6. v2→암호문 계정 이관과 늦은 기기·실패 복구 리허설.
7. 소수 테스트 계정, 이후 사용자 설명·복구 확인을 거친 전환.
8. 운영 평문·백업 정리와 보호 상태 공개, 정기 복구·배포 감사.

구현 전 결정할 항목은 다음과 같다. 본 문서의 권장값은 승인된 제품 정책이 아니다.

| 결정 | 권장안 | 선택의 영향 |
| --- | --- | --- |
| 최초 복구 수단 | 무작위 복구 키 + 기존 기기 승인 | 익숙하지 않지만 서버 비밀번호 의존과 guessing 위험 축소 |
| 기존 계정 전환 | 기기별 준비가 끝난 계정 단위 동의 전환 | 오래된 평문 계정이 남으므로 상태·지원 종료 정책 필요 |
| 백업 정리 | 운영 7일·기존 백업 30일 제안 | 복구 가능 기간과 평문 잔존 기간의 tradeoff |
| 로컬 잠금 | OS 재인증 + 잠금/절전 즉시 + 유휴 5분 | 사용 편의와 화면·키 접근 경계 |
| 서버 검색/반복 | 클라이언트로 이전 | 새 기기 최초 로딩·잠금 중 백그라운드 기능 제약 |
| 복잡한 협업 공유 | 초기 범위 제외 | 개인 vault 먼저 검증, 향후 공유 키 관리 별도 설계 |
| 서명/투명성 | 서명 업데이트 선행, 독립 witness 후속 평가 | 악성 서버의 분기·모든 서명자 침해는 잔여 위험 |

이 설계 완료는 구현 착수, 데이터 삭제, 운영 전환 또는 보안 보증을 승인한 것이 아니다.
