## PC

### P1. 재시작하면 매번 잠금을 풀어야 함

**현상**: 앱을 다시 켤 때마다(재부팅 후 자동 시작, 업데이트 재시작 포함) 잠금 화면이 뜨고, 버튼을 누른 뒤 Windows Hello 인증을 해야 한다.

**원인**
- 잠금 해제 상태는 main 프로세스 메모리에만 있다: `apps/desktop/public/electron/e2ee/workspaceService.js:30`, `:74-80`.
- 새 프로세스의 첫 bootstrap은 보관함이 있으면 무조건 잠금으로 답한다: `e2ee/applicationBootstrap.js:46-47`.
- 업데이트 재시작(`service/releaseAlert.service.js:180-185`)과 설정 변경 재시작(`configures/ipc.config.js:79-81`)도 같은 경로다.
- 데이터 키는 이미 Electron safeStorage(Windows DPAPI)로 감싸 저장돼 있다(`e2ee/localVault.js:44-48`, `modules/keyProtection.js:29-37`). Hello는 키를 만드는 데 쓰이지 않는 본인 확인 관문이다(`e2ee/vaultController.js:6-7`). 따라서 "건너뛰기"에 새 키 저장 방식은 필요 없다.

**구분할 잠금**: 이 항목은 앱 잠금(보관함)이다. 비밀 카테고리 잠금(`src/hooks/useSecretSession.js`)은 별개이며 어떤 안을 골라도 Hello를 계속 묻는다. PC에 시간 기반 자동 잠금은 없다. Windows 화면 잠금 · 절전 때 잠기는 동작(`e2ee/localStore.js:130-134`)도 별개다.

**선례**: 폰은 #83.3에서 "같은 부팅 안에서는 다시 켜도 바로 열림, 재부팅 후에만 인증"으로 정했다.

**해결 방법**
- A. 설정 토글 "앱을 다시 켤 때 잠금 화면 건너뛰기"(기본 끔) — 추천
  - `app-settings.json`에 boolean 키를 추가하고, 첫 bootstrap에서 설정이 켜져 있으면 main 내부에서만 보관함을 연다. 실패하면 지금처럼 잠금으로 답한다.
  - renderer가 이 방식을 요청할 수 없게 막는다.
  - 같은 실행 안에서 직접 잠그거나 화면 잠금 · 절전으로 잠긴 뒤에는 자동으로 열지 않는다(구분하지 않으면 잠그자마자 다시 열린다).
  - 토글을 켤 때 본인 확인을 한 번 받는다.
  - 범위 후보: A1 항상 / A2 같은 Windows 부팅 안에서만(폰과 같은 규칙. Windows 빠른 시작에서는 재부팅 판정이 부정확할 수 있음, 추정) / A3 업데이트 재시작 직후 한 번만.
- B. 잠금은 유지하고 잠금 화면이 뜨면 Hello 창을 자동으로 띄운다. Hello는 창에 포커스가 있어야 하므로 트레이 자동 시작 때는 창을 열 때 띄운다.

**영향 · 주의**
- 약해지는 것: Windows에 로그인된 PC 앞에 앉은 다른 사람이 Hello 없이 일반 할 일을 볼 수 있다. 비밀 카테고리는 계속 보호된다.
- 달라지지 않는 것: 같은 Windows 사용자로 도는 악성 프로그램은 지금도 DPAPI로 키를 풀 수 있다. 디스크 탈취 · 다른 Windows 계정에 대한 보호는 그대로다.
- 비밀번호만 쓰는 보관함에 적용하면 시작할 때 비밀번호가 아무 역할을 하지 않게 된다.

**사용자가 정할 것**
1. A / B / A3 중 어느 것인지, A라면 범위(A1 · A2).
2. 비밀번호만 쓰는 보관함에도 줄지.
3. "지금 잠그기" 후 앱을 껐다 켜면 잠금을 유지할지.
4. 토글 위치(설정 > 데이터의 앱 잠금 옆 / 설정 > 시스템).

### P2. 하루 안 기간에 날짜가 안 보임

**현상**: 오늘이 아닌 날의 하루 안 기간(예: 이틀 뒤 오후 7시 ~ 9시)이 목록에서 "오후 7시 ~ 9시"로만 보인다.

**원인**
- `apps/desktop/src/utils/periodDisplay.js:23-30`의 `periodText`가 시작과 끝이 같은 날이면 시각 범위만 반환한다. `now`를 받지 않아 오늘인지 판단하지 못한다. 호출은 `components/list/TaskRow.js:33`.
- 기한만 있는 행은 `utils/timeDisplay.js:100-107`에서 날짜를 붙인다(내일은 "내일 오후 7시", 2~6일 뒤는 "수 오후 7시", 그 밖은 "11월 24일").
- "이번 주" · "다음 주" · "나중에" · "기한 지남" 묶음, 묶지 않기, 검색 결과에서는 묶음 머리말도 날짜를 알려 주지 않는다.

**해결 방법**: `periodText`에 `now`를 넘기고 오늘이 아니면 날짜를 앞에 붙인다.
- 안1(추천): "11/17 오후 7시 ~ 9시". 빠른 추가 칩이 이미 이 형식이다. 오늘은 지금처럼 시각만.
- 안2: 기한 행과 같은 말("내일 오후 7시 ~ 9시", "수 오후 7시 ~ 9시", 7일 이상은 "11/24 …").
- 안3: 오늘 포함 항상 날짜.

**같은 누락 여부**: 타임라인 블록 머리와 캘린더 탭의 선택한 날 목록은 날짜 머리가 있어 문제 없다(이쪽은 시각만 유지해야 함). 상세 패널, 툴팁, 알림도 문제 없다.

**주의**: 목록 오른쪽 열은 최대 220px이고 줄바꿈이 없다(`components/list/TaskRow.scss:132-138`). P3의 연도까지 붙으면 한계에 가까우므로 구현 후 캡처로 확인한다.

**사용자가 정할 것**: 형식(안1 · 안2 · 안3).

### P3. 다른 해의 날짜가 월/일만 보임

**현상**: 다른 해(예: 2028.03.01, 2031년)의 기한이 목록에서 "3월 1일"로만 보인다.

**원인**: 아래 형식들이 연도를 넣지 않는다.
- `utils/timeDisplay.js:107`: 목록 기한 기본 형식 "묶음 맞춤"의 "M월 D일".
- `utils/periodDisplay.js:11` `monthDay` "M/D": 기간 행, 빠른 추가 칩, 선택한 날 목록의 "~11/12", 타임라인 띠, 툴팁.
- `utils/timeDisplay.js:86-90` `formatDueChip`(빠른 추가 칩).
- `utils/dateGroups.js:60-63` `dayLabel`: 기한 창의 시작 · 끝 칸, 요약, 직접 입력 미리보기.
- `molecules/pickers/DatePicker.js:266` `fieldDay`(기간 요약), `components/panel/CalendarTab.js:61`(선택한 날 머리).

이미 연도가 있는 곳: 상세의 기한 · 시작 · 끝, 기한 형식 "정확히" · "자세히". 올해가 아닐 때만 붙이는 관례도 이미 있다(상세의 만든 날, 반복 다음 날짜, 타임라인 제목).

**해결 방법**: 표시할 날짜의 연도가 지금 연도와 다르면 연도를 붙인다(기존 관례와 같은 규칙).
- 긴 형식: "2028년 3월 1일".
- 짧은 형식 후보: "2028/3/1"(추천) / "28/3/1" / "'28 3/1". 기간은 같은 해 안이면 한 번만("2028/3/1 ~ 3/5").
- 최소 범위: 목록 행(기한 · 기간), 빠른 추가 칩, 기한 창의 칸과 요약. 기한 창은 지금 달력 머리로만 연도를 알 수 있어 잘못 고르기 쉽다.

**주의**: P2와 같은 함수를 고치므로 함께 작업한다.

**사용자가 정할 것**: 짧은 형식의 연도 표기, 적용 범위(최소 범위 / 위 목록 전부).

### P4. 보기 옵션의 라벨과 옵션이 구분 안 됨

**현상**: 보기 옵션 창에서 묶음 머리말("묶기", "기한 없음 묶음", "정렬", "줄")과 그 아래 옵션이 비슷하게 보인다.

**원인**: 컴포넌트는 `apps/desktop/src/components/list/ListHeader.js:17-64`이고 전용 스타일 없이 공용 메뉴 스타일(`molecules/pickers/pickers.scss:467-499`)만 쓴다.

| 요소 | 크기 | 색 | 굵기 | 왼쪽 여백 |
| --- | --- | --- | --- | --- |
| 머리말 | 11.5px | #7f8a9c | 보통 | 10px |
| 옵션(선택 안 됨) | 13px | #a3acbb | 보통 | 10px |
| 옵션(선택됨) | 13px | #edf1f7 | 보통 | 10px, 오른쪽 끝에 체크 |

- 머리말과 옵션이 같은 왼쪽 선에서 시작하고 굵기가 같다. 차이는 1.5px 크기와 한 단계 회색뿐이다.
- 묶음 사이에 구분선이 없다(구분선은 "완료한 할 일 숨기기" 앞 한 곳뿐).
- 선택 표시가 글자 밝기와 오른쪽 끝의 작은 체크뿐이다.
- "남은 시간 보이기"는 체크 항목인데 라디오 옵션과 같은 모양이라 세 번째 선택지처럼 보인다.

**해결 방법(시안 후보)**
- 방향1: 구조 유지. 묶음마다 구분선, 머리말 굵게, 옵션 들여쓰기.
- 방향2: 방향1 + 옵션 왼쪽에 라디오/체크 표시, 선택된 줄에 옅은 배경.
- 방향3: 한 줄에 "라벨 + 두 칸 전환 버튼"(모든 묶음이 옵션 2개라 가능, 13줄이 6줄 정도로 줄어듦). 체크 항목은 스위치.
- 추천: 방향3 또는 방향2.

**주의**: 공용 메뉴 스타일은 할 일 오른쪽 클릭 메뉴도 쓰므로 보기 옵션 범위 안에서만 바꾼다. 방향3은 키보드 처리와 테스트도 고친다.

**사용자가 정할 것**: 방향, 창 너비(236px) 변경 가능 여부.

### P5. 할 일 상세에 삭제 버튼이 없음

**현상**: 상세 패널에서 할 일을 삭제할 방법이 없다.

**원인**: `components/panel/DetailPanel.js`와 패널 머리(`RightPanel.js:91-124`)에 삭제 동작이 없다. 삭제는 오른쪽 클릭 메뉴와 Del 키에만 있고, Del은 글자 입력 칸에 포커스가 있으면 동작하지 않는다(`components/TodoContent.js:574-590`).

**해결 방법**: `DetailPanel`은 이미 `actions`를 받고 있어 버튼에서 `actions.deleteTask(task.id)`만 부르면 기존 삭제 + 되돌리기 알림(#107, 확인 없음, 5초, Ctrl+Z)을 그대로 쓴다.
- 안1: 패널 머리의 × 왼쪽에 휴지통 아이콘.
- 안2(추천): 상세 맨 아래 "만든 날 …" 줄 오른쪽에 "삭제" 글자 버튼. 실수로 누를 위험이 가장 적다.
- 안3: 제목 줄의 별 옆에 "⋯"로 기존 할 일 메뉴 열기(삭제까지 두 번 누름).

**주의**: 제목 · 메모는 패널이 사라질 때 저장한다. 삭제 직후 이 저장이 이미 지워진 할 일로 가면 실패 알림이 뜨거나 되돌리기 스냅샷에 마지막 입력이 빠질 수 있다(추정, 실행 확인 안 함). 삭제 전에 입력을 먼저 저장하는 순서를 넣는다.

**사용자가 정할 것**: 위치, 좁은 창(서랍)에서 삭제 후 패널을 닫을지.

### P6. 시작 시각 0:00이 지정되지 않음

**현상**: 기간 창에서 시작 시간을 켜고 오전 12:00을 고르면 창 안에서는 그렇게 보이지만, 정한 뒤에는 "하루 시작"으로 돌아간다. 시작 알림도 울리지 않는다. 직접 입력 "0시~3시"도 같다.

**원인**
- 저장: `molecules/pickers/DatePicker.js:93-97` `composeStart`가 "시간 켬 + 0분"을 그날 00:00:00.000으로 만든다. 날짜만 정한 시작과 같은 값이다.
- 읽기: `utils/taskPeriod.js:13-16`과 `packages/e2ee/src/model/reminders.js:41-44`의 `hasStartTime`이 시 · 분이 0이면 "시각 없음"으로 본다. #109 데이터 계약(시작 00:00 = 날짜만)의 한계다.
- 끝 쪽: 0:00 끝은 정상이다. 23:59 끝은 "하루 끝"과 같은 값이라 같은 한계가 있지만, 끝 스위치의 기본값과 "하루 끝" 버튼이 같은 값이라 설계된 동작에 가깝다.

**해결 방법**
- 안A(추천): 시각 있는 0:00을 00:00:00.001로 저장하고 `hasStartTime`을 "시 · 분이 0이 아니거나 정확히 .001"로 바꾼다. 고칠 곳은 위 두 군데이며 필드가 하나라 복사 · 되살리기 · 반복에 추가 작업이 없다. 읽을 때 시작을 분 단위로 내림 처리한다(안 하면 길이가 "3시간"이 "2시간 59분"이 됨).
- 안B: 별도 필드. 옛 앱이 시작을 바꾸면 표시가 남아 잘못 읽히고 변경 범위가 크다.
- 안C: 데이터는 그대로 두고 0:00을 고르면 "하루 시작과 같아요"라고 안내만 한다. 0:00 시작 알림은 여전히 불가능하다(안내 문구가 생기므로 시안 필요).

**영향 · 주의(안A)**
- PC 2.6.0~2.6.1은 그 시작을 "하루 시작"으로 보여 주고 알림이 없다(지금과 같은 모습). 그 앱에서 시작을 바꾸면 그 앱의 값으로 새로 쓰인다.

## 모바일

### M1. 앱을 켤 때 오류 화면

**현상**: 앱을 켤 때 회색 화면에 빨간 오류 글이 잠깐 보였다가 본 화면으로 넘어간다.

**원인(일회성 테스트로 재현)**: 시작 시 "조용한 재개"와 잠금 화면의 "자동 잠금 해제"가 겹친다.
1. `apps/mobile/src/app/AppContext.tsx:184-188`: 계정이 복원되면 아직 저장소가 안 열려 phase가 `LOCKED`이고, 바로 이어 조용한 재개(`session.start()`)를 시작한다.
2. 재개는 Keystore 읽기와 DB 열기를 기다리는 동안 "진행 중" 표시를 켜 둔다(`core/vault/session.ts:39-45, 60-67`).
3. `app/navigation.tsx:165`의 로딩 조건은 phase가 없을 때만 스피너를 보여 주므로, `LOCKED`이면 잠금 화면을 그린다(`:198-199`).
4. 잠금 화면은 뜨자마자 자동으로 해제를 시도하고(`screens/setup/LockScreen.tsx:34-38`), 진행 중 표시 때문에 `UNLOCK_IN_PROGRESS` 오류를 받는다(`session.ts:40`).
5. 이 코드의 문구가 없어 `문제가 생겼어요 (UNLOCK_IN_PROGRESS).`가 빨간 글로 뜬다(`ui/messages.ts:57`, `ui/kit.tsx:572-586`).
6. 재개가 끝나면 본 화면으로 넘어간다.

가짜 Keystore에 40ms 지연을 넣으면 "Thread가 잠겨 있어요 → 문제가 생겼어요 → 모든 할 일" 순서로 재현됐고, 지연이 0이면 보이지 않았다. 실기기의 Keystore 호출은 항상 비동기라 매번 보일 조건이다. 2.0 화면 구현 때부터 있던 문제이며 #108~#110과는 무관하다.

같은 원인의 다른 증상: 재부팅 뒤 첫 실행에서는 자동 해제가 같은 오류로 실패해, 생체 인증 창이 자동으로 뜨지 않고 빨간 글이 버튼을 누를 때까지 남는다.

**그 밖의 후보(가능성 낮음)**: 공유 패키지 변경(2.1.0 출시 뒤라 무관, tsc · jest 통과), JS 예외(릴리스에서는 빨간 화면이 아니라 앱 종료가 됨), "보관함을 열 수 없어요" 화면(잠깐이 아니라 계속 남음).

**해결 방법**
- A(추천): 재개가 끝날 때까지 잠금 화면을 그리지 않고 스피너를 유지한다. 재개가 실패한 경우(재부팅 뒤)에만 잠금 화면이 뜨고 자동 해제가 정상 동작한다.
- B(A와 함께 권장): 잠금 화면에서 `UNLOCK_IN_PROGRESS` · `UNLOCK_CANCELLED`는 오류로 표시하지 않는다.
- C: 세션의 해제가 진행 중인 재개를 기다리게 한다. 세션 계약이 바뀌어 영향이 가장 넓다.
- "같은 부팅 재시작 시 잠금 화면 · 오류 글이 한 번도 안 보인다"는 회귀 테스트를 추가한다.

**사용자가 확인할 것**: 보인 화면이 "자물쇠 + Thread가 잠겨 있어요 + 빨간 글 `문제가 생겼어요 (UNLOCK_IN_PROGRESS).`"가 맞는지. 재부팅 직후에는 글이 계속 남아 확인하기 쉽다. 아니라면 글 내용과 설치본 종류(Play 릴리스 / 개발 빌드)가 필요하다.

### M2. 하위 할 일 수정 불가

**현상**: 폰 상세 화면에서 하위 할 일 이름을 고칠 수 없다.

**원인**: `apps/mobile/src/screens/app/TaskDetailScreen.tsx:220-260`의 하위 할 일 행은 체크, 읽기 전용 제목, 삭제 X뿐이다. 이름 바꾸기 UI가 처음부터 없다.

| 동작 | 공유 모델 | 폰 UI |
| --- | --- | --- |
| 추가 | `task/createSubtask` | 있음(키보드 완료 키로만) |
| 완료 전환 | `task/updateSubtaskDone` | 있음 |
| 삭제 | `task/deleteSubtask` | 있음(확인 · 되돌리기 없이 즉시) |
| 이름 바꾸기 | `task/updateSubtaskTitle` | 없음 |
| 순서 바꾸기 | `task/updateSubtaskOrder` | 없음(표시 순서만 PC와 같음) |

부수 문제: 추가 칸에 글을 쓰고 완료 키를 누르지 않은 채 다른 곳을 누르면 추가되지 않는다.

**해결 방법**
- A(추천, 최소): 제목을 입력 칸으로 바꾸고 포커스가 빠지거나 완료 키를 누를 때 값이 바뀌었으면 `task/updateSubtaskTitle`을 보낸다. 공유 모델 · 서버 변경은 없다.
- B: A + 추가 칸에서 포커스가 빠질 때도 추가(또는 추가 버튼).
- C: B + 순서 바꾸기. 끌기 라이브러리가 없어 의존성 추가나 위/아래 버튼이 필요하다.

**주의**: 빈 이름 처리 규칙, 다른 기기의 변경이 편집 중인 글을 덮어쓰지 않게 하는 동기화, X 버튼이 편집 칸 옆이라 잘못 눌러 삭제할 위험.

**사용자가 정할 것**: 이름 바꾸기만인지 순서도 포함인지, 이름을 비우면(원래 이름으로 / 삭제), 편집 시작 방식(누르면 바로 / 길게 누르기 / 연필), 삭제 방식(즉시 / 확인 / 되돌리기 알림), 추가 칸 동작.

### M3. 하위 할 일 입력이 키보드에 가려짐

**현상**: 상세 화면에서 "하위 할 일 추가" 칸을 누르면 키보드가 입력 칸을 덮는다. 메모 칸도 같다.

**원인**
- Android가 엣지 투 엣지라 `adjustResize`가 창을 줄이지 않는다(`android/gradle.properties`의 `edgeToEdgeEnabled=true`, targetSdk 36). 키보드는 이벤트로만 전달되므로 JS에서 직접 피해야 한다.
- `TaskDetailScreen`에 키보드 회피가 없다. 최상위가 일반 `View`(86행)이고 `ScrollView`(115-118행)에 아래 여백 40뿐이다. 앱에서 키보드 회피를 쓰는 곳은 `ui/kit.tsx`의 `Screen`과 `Sheet`뿐이고 상세 화면은 둘 다 쓰지 않는다.
- 연속 추가(`blurOnSubmit={false}`)를 하면 행이 늘 때마다 입력 칸이 더 내려간다.
- iOS도 같은 코드라 같은 증상일 것이다(실기기 미확인).

**해결 방법**
- A(추천): 상세 화면을 `KeyboardAvoidingView`로 감싸고(상단 inset만큼 offset 필요), 하위 할 일 입력 · 메모 포커스 때와 추가 직후 해당 위치로 스크롤한다.
- B: iOS는 `automaticallyAdjustKeyboardInsets`, Android만 A.
- C: `react-native-keyboard-controller` 도입(네이티브 의존성 추가, 이번 범위에는 과함).

**주의**: M2의 행 편집 칸에도 같은 처리가 필요하므로 한 작업으로 묶는다. 카테고리 이름 편집 화면도 목록이 길면 가려질 수 있다(추정).

**사용자가 확인할 것**: 메모 칸도 포함인지, 기기와 Android 버전, 카테고리 편집 화면도 같이 고칠지.

## 참고: 폰에 기간 · 할 일별 알림을 넣는 범위

공유 모델은 준비돼 있다(`task/updateTaskPeriod`, `task/updateTaskAlert`, `planReminders(…, { periods: true })`). 폰은 지금 `start_offset` · `alert_*`를 읽지 않지만, 기한을 옮기면 길이가 유지되고 기한을 지우면 시작도 지워지므로 데이터는 깨지지 않는다.

손댈 곳: 모델 보기(`core/model/view.ts`, `timeDisplay.ts`), 날짜 고르기 시트(`ui/DateTimeSheet.tsx`, 가장 큰 작업), 상세 · 목록 · 캘린더 · 타임라인 화면, 알림 계획과 설정(`core/reminders.ts`, `core/prefs.ts`, `ReminderSettings.tsx`). PC의 계산 도우미(`apps/desktop/src/utils/taskPeriod.js`)는 공유 패키지로 옮기거나 다시 써야 한다. 화면 대부분이 바뀌어 폰 전용 시안이 필요하고, M1~M3보다 훨씬 큰 별도 태스크 규모다.
