# 데스크톱 앱 내 업데이트가 동작하지 않던 결함

작성: 2026-10-03 01:29 (KST) · 영향 버전: 2.0.0, 2.0.1 · 수정: 2.0.2 (`f2ec380`)

## 현상

2.0.1을 TUF 저장소에 게시한 뒤, 실행 중이던 2.0.0 설치본의 상단 바에 업데이트 표시가 나타나지 않았다. 오류 안내도 없었다.

| 확인 | 결과 |
| --- | --- |
| 게시 저장소 | `verifyPublishedRepository` 일치(8개 파일). 2.0.0과 같은 검증 코드로 새 캐시와 repo-1 캐시 모두에서 2.0.1을 찾음 |
| 설치본 캐시 | 앱 시작(2026-10-02 15:10:19) 2초 뒤 첫 확인에서만 `releases.json`이 기록되고 이후 10시간 동안 메타데이터·카탈로그 갱신이 없음 |
| 재현 | 같은 `TrustedUpdates` 인스턴스로 두 번째 `latest()`를 호출하면 `Cannot update timestamp after snapshot` |

## 원인

`TrustedUpdates`가 생성 시 tuf-js `Updater`를 하나 만들어 계속 재사용했다. tuf-js의 `Updater`는 신뢰 메타데이터 집합을 하나만 가지며 `refresh()`는 인스턴스당 한 번만 성공한다. 두 번째 호출부터는 이미 snapshot을 읽은 상태에서 timestamp를 다시 갱신하려 해 예외가 난다.

그 결과 한 프로세스에서 다음이 모두 실패했다.

- 시작 후 첫 확인을 제외한 30초 주기·포커스·동기화 연결 시 확인
- 업데이트 다운로드(`download`)
- 설치 직전 검증(`verifyBeforeInstall`)

`ReleaseAlertService.check()`가 네트워크 장애 시 기존 알림을 유지하려고 예외를 삼켜서 실패가 드러나지 않았다. 기존 테스트의 가짜 `Updater`는 `refresh()`마다 신뢰 집합을 새로 만들어 이 제약을 반영하지 못했다.

첫 확인은 성공하므로 앱을 재시작하면 표시는 나타나지만, 다운로드에서 실패한다. 2.0.0과 2.0.1은 앱 안에서 다음 버전으로 업데이트할 수 없다.

## 조치

| 항목 | 내용 |
| --- | --- |
| 수정 | 작업마다 새 `Updater`를 만들고 같은 캐시 디렉터리를 쓴다. 캐시의 timestamp/snapshot이 롤백 기준으로 계속 쓰인다. 같은 캐시에 쓰므로 작업은 하나씩 실행한다 |
| 테스트 | 가짜 `Updater`가 실제 `TrustedMetadataStore`를 인스턴스당 하나만 쓰게 바꾸고, 반복 확인·동시 확인과 다운로드·설치 전 검증을 추가. 기존 코드에서 실패, 수정 후 통과. 데스크톱 node 테스트 237개 통과 |
| 운영 저장소 확인 | 수정 코드로 게시 저장소에 대해 확인 2회 → 2.0.1 다운로드 → 설치 전 검증 통과 |
| 배포 | 2.0.2 빌드, `repo-3` 생성·검증 후 게시(2026-10-03 01:32, 게시 파일 9개 대조 일치). 사용자 PC는 2.0.2를 수동 설치해 확인 |

## 남은 영향과 후속

- 2.0.0·2.0.1 설치본은 수동으로 2.0.2 이상을 설치해야 한다. 현재 사용자는 1명이며 2.0.2 설치를 마쳤다.
- 앱 안 업데이트: 2.0.2 설치본에서 2.0.3 알림·다운로드·설치·재시작이 정상 동작함을 사용자가 확인했다(2026-10-03 16:12).
- 확인 실패가 계속될 때 사용자에게 보이는 표시가 없다. 반복 실패를 알리는 방법은 별도로 검토한다.
