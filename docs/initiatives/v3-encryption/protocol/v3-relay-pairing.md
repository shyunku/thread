# v3 서버 중계 기기 연결 (설계안)

작성: 2026-10-03 (KST) · 상태: 설계 검토 중 · [#76](../../../tasks/0076.md)

## 목적

지금의 PC↔PC 연결은 사용자가 64자 보관함 지문을 새 기기에 입력하고, 새 기기의 요청(QR 캡처 또는 요청 파일)을 쓰던 기기로, 쓰던 기기의 승인 파일을 다시 새 기기로 손으로 옮겨야 한다. 이 문서는 요청과 승인을 **서버가 중계**하고, 사용자는 양쪽 화면의 **6자리 숫자가 같은지만 확인**하는 방식을 정의한다. 기존 QR·파일 방식은 "다른 방법"으로 남긴다.

## 위협 모델

| 대상 | 가정 |
| --- | --- |
| 서버 | 저장·전달은 하지만 내용은 믿지 않는다. 요청을 바꿔치기하거나 다른 보관함을 보여 줄 수 있다고 가정한다. 가용성(전달 거부)은 막지 않는다 |
| 두 기기 | 같은 계정으로 로그인해 있다. 쓰던 기기(E)는 기기 승인 권한과 확인된 소유자 키를 가진다. 새 기기(N)는 로컬 보관함만 만든 상태다 |
| 사용자 | 두 화면의 6자리 숫자를 비교하고, 같을 때만 양쪽에서 "같아요"를 누른다 |

기존 방식에서 64자 지문 입력과 요청 지문 비교가 막던 공격(서버가 가짜 보관함이나 가짜 기기 요청을 끼워 넣는 것)을, 이 방식에서는 **커밋 후 공개하는 난수로 만든 6자리 확인 숫자**가 막는다. 블루투스 Numeric Comparison과 같은 구조다.

## 흐름

| 순서 | 주체 | 동작 |
| --- | --- | --- |
| 1 | E | 사용자가 "새 기기 추가"를 연다. E는 32바이트 난수 `nE`를 만들고, 보관함 ID·보관함 지문(genesis fingerprint)·`cE = SHA-256("thread-pair-commit-v1" ‖ nE)`를 서버에 올린다(세션 생성) |
| 2 | N | 사용자가 "쓰던 기기로 연결"을 고르면 계정의 현재 세션을 받는다. 받은 보관함 지문으로 서버의 멤버십 이력을 검증하고(기존 `historyFor`), 기존 형식의 연결 요청 `R`(기기 공개키, 서명, 10분 만료)과 32바이트 난수 `nN`을 올린다 |
| 3 | E | `R`과 `nN`을 받아 `R`의 서명·만료·보관함을 검증한 뒤 `nE`를 공개한다 |
| 4 | N | `SHA-256(... ‖ nE) = cE`를 확인한다 |
| 5 | 양쪽 | `SAS = SHA-256("thread-pair-sas-v1" ‖ 보관함 지문 ‖ requestFingerprint(R) ‖ nE ‖ nN)`의 앞 8바이트를 정수로 읽어 10⁶으로 나눈 나머지를 6자리로 표시한다 |
| 6 | 사용자 | 두 화면의 숫자를 비교한다. N에서 "같아요"를 누르면 N은 승인을 기다린다. E에서 "같아요, 승인"을 누르고 재인증(Windows Hello/비밀번호)한다 |
| 7 | E | 기존 `approveRequest` 경로로 멤버십 이벤트를 서버에 커밋하고, N의 암호화 키로 봉인한 키 전달 데이터(기존 승인 파일 내용)를 세션에 올린다 |
| 8 | N | 전달 데이터를 받아 기존 `acceptFile` 검증(서명자 권한, 멤버십 이력, 봉인 해제)을 거쳐 연결을 끝낸다 |

## 왜 안전한가

- **보관함 바꿔치기:** 서버가 N에게 가짜 보관함 지문을 주면 N의 숫자는 그 지문으로 계산된다. E의 숫자는 진짜 지문으로 계산되므로, 공격자가 양쪽 숫자를 맞추려면 아래 조건에 걸린다.
- **숫자 맞추기 공격:** 공격자는 한쪽 숫자를 결정하는 값을 상대의 난수를 보기 전에 정해야 한다.
  - E 쪽: 공격자가 가짜 `R'`, `nN'`를 보낸 뒤에야 E가 `nE`를 공개한다.
  - N 쪽: 공격자가 가짜 `cE'`를 먼저 보내야 N이 `nN`을 보낸다.
  - 어느 순서로 진행해도 마지막 값이 공격자가 고를 수 없는 난수라, 숫자가 우연히 같을 확률은 1/10⁶이다. 실패한 시도는 사용자가 보게 되고 요청은 10분 뒤 만료된다.
- **키 전달:** 전달 데이터는 N의 공개키로 봉인되고 E의 기기 서명이 붙는다. 서버는 열 수 없고, N은 기존과 같은 검증을 한다.
- **승인 권한:** 서버에 올라간 세션만으로는 아무 일도 일어나지 않는다. 멤버십 변경은 기존처럼 E의 재인증과 서명이 있어야 한다.

## 서버 API (v3, 계정 토큰 필요)

세션은 계정마다 하나이며 Redis에 10분 동안만 둔다. 새 세션을 만들면 이전 세션은 지워진다. 서버는 단계 순서와 한 번만 쓰기를 강제하지만, 보안 판단은 기기가 한다.

| 요청 | 주체 | 본문 | 결과 |
| --- | --- | --- | --- |
| `POST /v3/pairing/session` | E | `vaultId`, `fingerprint`, `commitment` | 세션 ID, 만료 시각 |
| `GET /v3/pairing/session` | 양쪽 | — | 현재 세션의 공개 값 전부(없으면 404) |
| `POST /v3/pairing/session/request` | N | `sessionId`, `request`(≤2KB), `nonce` | 단계 갱신 |
| `POST /v3/pairing/session/reveal` | E | `sessionId`, `nonce` | 단계 갱신 |
| `POST /v3/pairing/session/transfer` | E | `sessionId`, `transfer`(≤512KB) | 단계 갱신 |
| `POST /v3/pairing/session/cancel` | 양쪽 | `sessionId` | 세션 삭제 |

양쪽은 화면이 열려 있는 동안 2초 간격으로 `GET`을 확인한다.

## 기존 방식과의 관계

- 요청 레코드, 멤버십 이벤트, 키 전달 형식은 바꾸지 않는다. 중계는 이 값들을 나르는 통로만 바꾼다.
- QR·요청 파일·승인 파일 방식은 "다른 방법"으로 남긴다. 서버 중계가 막혔을 때 쓴다.
- 기존 방식의 64자 지문 입력은 "다른 방법"에서만 쓴다.

## 남은 검토

- 숫자 비교 대신 짧은 코드 입력(PAKE)은 구현 위험이 커서 제외했다.
- 한 계정에서 두 사람이 동시에 기기를 추가하는 경우는 고려하지 않는다(개인용 서비스). 세션은 마지막 하나만 유효하다.
